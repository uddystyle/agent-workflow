# 実装を通す

**この skill は繋ぐだけである。** どう書くか、どう見るかは各 skill と `AGENTS.md` が持つ。
ここが持つのは**順序**と、飛ばしやすい段を引き戻すことだけ。

🔴 **飛ばした段は、後から埋まらない。** 起点を決めずに書き始めればレビューは範囲を決められず、
検査を後回しにすれば「通ったこと」が何を意味するか誰にも言えない。

## 1. 隔離を頼む

編集する agent は worktree の中で動かす（`DECISIONS.md` D-21）。

🔴 **自分で worktree を作らない。** 作成と削除は作業場所と branch を増減させるので、**人が決める**
（`worktrees` skill は人が呼ぶ側に立ててある）。隔離されていなければ、**人に頼んで待つ**。

**完了条件**: `git worktree list` に対象があり、いま居る場所がそこである。

## 2. 起点を1つ決める

レビューも測定も、**同じ起点**を要る。後から決めると範囲が動く。

```sh
git rev-parse --short HEAD    # ここから先が今回の変更になる
```

**完了条件**: 起点のコミットを1つ言える。⚠️ 「だいたいこのへん」は起点ではない。

## 3. 検査を先に書き、緩めて落ちることを見る

`AGENTS.md` の Repository 節が正本である。ここでは順序だけ言う——**検査が先**。

🔴 **書いた検査は、わざと緩めて落ちるところまで見る。** 落ちなければ、その検査は何も守っていない。

**完了条件**: 新しい検査それぞれについて、**緩めたら落ちた**と言える。

## 4. 作る

型検査と単体はこまめに、**全体は最後に1回**。何を走らせるかは `AGENTS.md` の Repository 節が持つ。

⚠️ **repo の外に副作用がある検査は隔離して回す**——素で走らせると環境が書き換わる。

**完了条件**: 全体の検査が通っている。落ちたものを「関係ない」で流していない。

## 5. 2つの観点で見る

`two-axis-review` を **§2 の起点**で当てる。規約とスペックを別々に見る（D-1）。

**完了条件**: 2つの観点が独立に走り、指摘それぞれに根拠と「確かめたか」が付いている。

## 6. 結果を commit に残す

レビューを終えた commit に、trailer を1行足す（`NEXT.md` §4）。

```
Reviewed: pass    # 直しは出なかった
Reviewed: fix     # 直してから通した
```

🔴 **台帳を作らない**（D-7）。記録は、それが説明している commit の上に置く。
⚠️ **付け忘れた1本は数えられない。** 忘れた分を「通った」に混ぜない。

**完了条件**: commit に `Reviewed:` が付いている。push するかは人が決める。
