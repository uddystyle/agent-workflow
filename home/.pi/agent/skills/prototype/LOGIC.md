# 状態の動きを確かめる試作

**紙で追えない状態機械を、押して確かめられる形にする。**

作るのは **HTML 1枚**。何も入れずに、**ダブルクリックで開く**もの。

## 1. 問いを言う

「どの順で押すと、どうなるか分からない」を1文にする。
⚠️ **その1文を HTML の先頭に書く。** 後で見た人が、何を確かめた物か分かるように。

**完了条件**: 問いが1文で書かれ、HTML の先頭にある。

## 2. ロジックを純粋な塊にする

🔴 **`<script>` の中に、DOM を触らない小さな module として置く。**
`document` も、ボタンの処理も、その中に入れない。

理由は2つ。**本体へ畳むときにそのまま移せる**こと。そして**状態の遷移だけを読める**こと。

**完了条件**: ロジックの塊を読むだけで、状態がどう変わるかを追える。

## 3. 画面を4つの部品で作る

**順番も守る。**

1. **表題と1行の説明** —— この demo で何を試せるか
2. 🔴 **いまの状態** —— 関係する状態を**全部**、**ラベル付きの欄**として出す。
   ⚠️ **JSON をそのまま吐かない。** 読む人は開発者とは限らない。**押すたびに描き直す**
3. **自由に押せるボタン** —— 操作1つにつき1つ。**いつでも押せる**
4. **案内つきの筋書き** —— 場面ごとにタブを分け、平易な説明と**順番に押すボタン**を置く

⚠️ **筋書きの各段は、本物のボタンである。** 押すとその操作が実行され、次の段へ進む。
筋書きを始めると、**既知の初期状態に戻る**。

**完了条件**: 開発者でない人が、説明を読んで押せる。

## 4. 渡して、待たない

ファイルの場所を伝える。⚠️ **こちらでターンを終える。** 覗きに行かない。

**完了条件**: 場所を伝え、何を見てほしいかを1文で言った。

## 5. 答えと試作を捕まえる

- **答え** —— 決着した問いと結論。判断の置き場へ
- **試作** —— 捨てブランチへ commit するか、消すか

**完了条件**: 答えの置き場を言え、試作を残したか捨てたかを言える。

## やってはいけない形

- ⚠️ **状態を一部しか出さない** —— 出していない部分で説明がつく現象を、見逃す
- ⚠️ **筋書きだけで、自由に押せない** —— 想定した順序しか試せない
- 🔴 **ロジックが DOM に絡む** —— 本体へ畳めず、書き直しになる
