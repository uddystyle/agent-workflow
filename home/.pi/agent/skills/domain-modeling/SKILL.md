# 言葉を揃える

**コードの話とドメインの話を分ける。** 「サーバ専用のコードはここに置く」は作りの話で、
「同じ番号は同じ人を指す」はドメインの話である。**後者だけがここの対象**。

🔴 **想像で書かない。** 用語はコードとスキーマの中と、人の頭の中にある。引けるものは引き、
引けないものは**聞く**。

## 1. 引けるものから種を作る

名前は実在するところから取る。

```sh
git ls-files | grep -iE 'migration|schema'    # 表と列の名前
git grep -ohE 'type [A-Z][A-Za-z]+|interface [A-Z][A-Za-z]+' | sort -u
```

**完了条件**: 候補の語が、それぞれ**どのファイルから取ったか**を言える。

## 2. 曖昧な語を、具体の場面で尖らせる

「ユーザ」「状態」「セッション」のような語は、**場面を1つ挙げると割れる**。

- その語が指すものを**2つ挙げられる**なら、語が足りていない
- コードでの呼び名と、人が話すときの呼び名が**違う**なら、どちらが正かを決める

⚠️ **決めた語は、コードにも戻す。** 文書だけ直しても、次に読む人はコードの語を見る。

**完了条件**: 尖らせた語それぞれについて、**指すものが1つ**に定まっている。

## 3. `CONTEXT.md` に置く

repo 直下に置く。既に置き場の慣行があるならそちらに合わせ、**無ければ置いた場所を言う**。

🔴 **`AGENTS.md` に置かない。** あれは毎回 context に載り、上限がある。
**用語は増え続ける**ので、上限のある場所に置くと、いつか用語か規約のどちらかを削ることになる。

⚠️ **他プロジェクトの語を、道具の repo に持ち込まない。** ドメインは、そのドメインの repo に置く。

**完了条件**: `CONTEXT.md` の各項目が、**コードのどこに現れるか**を1つ以上指している。

## 4. 判断を書くのは、3つとも満たすときだけ

用語を詰めると判断が出る。**全部は書かない。**

1. **戻しにくい** —— 後で向きを変えるのに実費がかかる
2. **文脈が無いと驚く** —— 後から読む人が「なぜこうなっている」と問う
3. **本物のトレードオフだった** —— 選ばなかった案が実在した

🔴 **1件1ファイルに割らない。** 判断は1箇所に積む——割ると「どちらを見ればよいか」が分からなくなる。
⚠️ この repo 群では、判断の置き場は**既にある**。新しく作る前に探す。

**完了条件**: 書いた判断それぞれが3条件を満たす。満たさないものは**書かずに捨てた**と言える。
